# Evaluation Criteria

Version: 18
Last updated: 2026-08-28

## How to use this file

- Define criteria before the output is evaluated.
- Give each criterion a stable ID.
- Mark each criterion as `Required` or `Advisory`.
- Make each pass condition observable and specific.
- Identify how each criterion will be verified.
- Record actual results in `feedback/`, not in this file.
- Increment the version and explain any material criterion change.

## Required criteria

| ID | Criterion | Pass condition | Verification method |
| --- | --- | --- | --- |
| LOOP-01 | Fill-until-full processing reaches a stable state. | The tester scans, fills reachable empty fields, triggers updates, waits, and rescans until no new reachable empty fields remain or the configured safety limit is reached. | Instrumented browser test against representative CHEFS forms. |
| FIELD-01 | Common user-facing fields are populated. | Supported visible input components receive valid synthetic values without overwriting protected or already populated values unless explicitly intended. | Component coverage suite and browser inspection. |
| FIELD-02 | Rendered numeric and date constraints produce valid synthetic values. | When a custom CHEFS component omits usable Form.io min/max metadata, the tester derives numeric and calendar bounds from unambiguous rendered guidance, keeps generated values inside those bounds, and can populate a rendered Flatpickr-backed date control without requiring a Form.io component lookup. | Execute `evals/tests/field-constraint-regression.test.js` and replay run `AC1EC1` against the authorized UAT form. |
| FIELD-03 | Optional remote and preconfigured components are populated semantically. | Reachable optional OrgBook and Simple BC Address controls perform a search and select a returned item. OrgBook resolves the rendered wrapper against every discoverable live page-context Form.io root instead of relying on the first cached form instance, prefers the component that owns the exact wrapper, and reports bounded root/component lookup diagnostics. It then calls `triggerUpdate('wonderful', true)`, awaits `itemsLoaded`, confirms `WONDERFUL FLOORING` exists in `selectOptions`, calls `setValue('WONDERFUL FLOORING')`, triggers change processing, and keeps the selected value present through a bounded stability window and later rescan. Synthetic Choices interaction is only a fallback. A remote control never falls back to selecting its hidden native placeholder. Map controls create a selected location or marker instead of treating search text as a value; CHEFS file controls retain an uploaded synthetic attachment. A typed query, placeholder, transient choice state or result list alone never counts as a completed selection. | Execute `evals/tests/autocomplete-editgrid-regression.test.js`, including the multiple-Form.io-root bridge fixture, and replay the TEST Import form against the authorized TEST environment. |
| COND-01 | Conditional content is handled. | Newly revealed components are discovered and populated on a later pass. | CHEFS form fixture with nested conditional sections. |
| TAB-01 | Tabbed content is handled. | Reachable fields across tabs are discovered and populated. | Multi-tab CHEFS form fixture. |
| GRID-01 | Data grids are handled. | Two coherent rows are added and populated unless configuration specifies another count. | CHEFS form fixture containing representative data grids. |
| GRID-02 | Edit Grid rows are committed without hijacking form submission. | After nested fields are populated, every open Edit Grid row is saved before validation; row-level Save, Cancel, Remove, Delete and close controls are excluded from form-submit discovery, and the actual Form.io submit component is selected. | Execute `evals/tests/autocomplete-editgrid-regression.test.js` and replay run `BE27D7` against the authorized UAT form. |
| UPLOAD-01 | File uploads are complete, bounded and non-blocking to later fields. | A rendered filename does not count as complete while a visible upload progress indicator or pending-upload message remains. The preferred rendered drop path has one cumulative bounded wait, never redispatches the same pending file, records timeout/failure evidence, and releases the fill loop so later components can be processed. | Execute `evals/tests/upload-stop-regression.test.js` and replay the TEST Import form containing optional `simplefile` and later Edit Grid components. |
| MASK-01 | Input masks produce suitable values. | Values satisfy supported `9`, `a`, and `*` masks and remain appropriate to the field label. | Mask fixture suite and Form.io validation results. |
| VALID-01 | Validation recovery is attempted safely. | Actionable validation errors trigger bounded correction attempts and unresolved errors are reported. | Invalid-first fixture and diagnostic event inspection. |
| SUBMIT-01 | The default workflow submits when the form is valid. | A valid form on an approved domain is submitted and final confirmation data is captured. | Authorized non-production end-to-end test. |
| STOP-01 | Stop Run interrupts an in-flight operation and finalizes promptly. | Selecting Stop Run sets the cancellation state, rejects pending page-bridge waits, makes polling loops exit, and idempotently finalizes the run as `stopped` without waiting for the current field timeout. The popup acknowledges the request and refreshes to terminal state. | Execute `evals/tests/upload-stop-regression.test.js` and manually stop during an authorized slow upload. |
| SAFE-01 | Automatic submission is domain restricted. | Automatic submission is blocked on every domain not explicitly allowlisted. | Allowlist and denylist browser tests. |
| DATA-01 | Generated identities and personal details are synthetic. | Generated submission values contain no supplied or discovered real personal data. | Generator review and representative output inspection. |
| DATA-02 | Generated email addresses are tasteful, coherent synthetic identities. | Generated email values contain none of `test`, `fake`, or `example`, contain no CHEFS product identity, and use the fictional `cedarridgecommunity.ca` domain associated with the generated organization. | Execute `evals/tests/generated-email-regression.test.js`. |
| PID-01 | Instrumentation excludes PID. | No PID appears in diagnostic events, logs, exported bundles, or confirmation data. | Automated sensitive-field scan plus manual bundle review. |
| DIAG-01 | Every run produces traceable diagnostics. | The export includes extension version, build ID, session ID, form metadata, per-pass events, discovery, fill outcomes, validation, submission attempts, errors, and final confirmation data. | Diagnostic schema validation and representative bundle inspection. |
| EXPORT-01 | Manual exports honor an optional validated Downloads-relative folder preference. | Settings labels the field `Export Folder`, its default is blank, no machine-specific folder appears in runtime defaults or guidance, blank routes the filename directly to Downloads, a valid relative subfolder prefixes the filename, and unsafe path forms are rejected before settings are saved. | Automated UI/default/migration/path regression plus browser Save As inspection with blank and tester-selected relative-folder configurations. |
| EXPORT-02 | Finalized terminal runs can export automatically without an extension-requested confirmation dialog. | When `Automatically export after each run` is enabled, exactly one download with `saveAs: false` is requested after each finalized `submitted`, `completed`, `failed`, `stalled`, `blocked`, `safety_stop`, or `stopped` outcome. | Automated lifecycle regression plus authorized non-production browser tests covering success and representative failure. |
| EXPORT-03 | Automatic exports contain finalized success or failure evidence and report export state independently. | Automatic export begins only after terminal snapshots, checkpoints, failure details, and attempted failure screenshot capture are persisted; its pending, successful, or failed state is retained per run, duplicate finalization messages do not create duplicate downloads, and an export failure does not change the terminal run result. | Automated lifecycle/order/idempotency regression and representative success/failure ZIP inspection. |
| EXPORT-04 | Select safely feeds the existing Downloads-relative Export Folder setting. | Select begins in Downloads, derives a candidate folder name, passes it through the existing relative-path validator, proves that the selected directory maps to the direct Downloads child by creating and detecting a unique probe download, removes the probe file and history entry, and populates the field only after success. Cancellation, unsafe names, arbitrary locations, nested locations that cannot be represented, download-policy failure, or validation failure leave the prior field value unchanged. No directory handle is retained and the existing export engine remains unchanged. | Mocked folder-picker/probe regression plus managed Chrome tests for a valid direct Downloads child and an arbitrary location. |
| BATCH-01 | A project-level launcher opens an embedded regression list without depending on an extension ID. | A batch file outside the extension folder contains editable form URLs, opens each URL in Chrome with a fragment-only suite marker, sequence number and configured launcher token, and degrades safely to opening tabs when the extension is absent. | Batch-file static regression and managed Chrome launch test. |
| BATCH-02 | External batch activation is explicit and restricted. | Batch launching is disabled by default; a valid per-install token, an exact configured origin, granted optional host permission and the existing approved non-production environment check are all required before a marked tab can enter the run queue. Invalid tokens, unconfigured origins, missing permissions and production-like hosts never start a run. | Service-worker orchestration regression plus permission and denylist browser tests. |
| BATCH-03 | Marked regression tabs execute through a persistent sequential queue. | Eligible tabs are queued in sequence order, only one batch run is active, the active tab is selected before execution, terminal finalization and automatic export complete before the next run starts, and queue state survives service-worker restart through extension storage. | Mocked multi-tab orchestration/restart regression and representative browser suite. |
| BATCH-04 | Batch operation is observable and stoppable. | The popup reports active, queued and completed counts; Stop Batch clears queued work and requests stop for the active run; closed tabs and startup failures are recorded without wedging the queue; completed history is bounded. | Mocked stop/closed-tab/start-failure regression plus popup inspection. |
| BATCH-05 | Batch startup coordinates tab creation and actual CHEFS readiness. | Queue processing waits for a bounded quiet period after marked tabs arrive, activates the selected tab, and does not create a run until the Form.io form is mounted. The popup distinguishes suite preparation from waiting for a form, and a form that never becomes ready fails without blocking later items. | Mocked tab-arrival/readiness regression plus managed Chrome eight-form launch. |
| BATCH-06 | Established runs remain sequential and are not mistaken for launcher startup failures. | Once a run record exists, the launcher timeout cannot release its queue slot. A responsive content controller can answer a watchdog liveness probe during a long field operation, while an unresponsive controller still reaches the bounded stall path. No later batch item starts before the active run finalizes and completes its automatic export attempt. | Mocked long-run/timeout/watchdog regression plus REDIP workplace replay. |
| UX-02 | Popup secondary actions use the available width coherently. | Export and Copy may share a row; Settings spans the full popup width; Stop Batch spans the full width when visible. | Popup markup/style regression and popup screenshot inspection. |
| DASH-01 | Results dashboard opening is opt-in, idempotent and context aware. | A disabled-by-default setting controls automatic opening. A singleton opens the dashboard once after finalization/export; a batch opens it once after the whole queue completes. An existing dashboard tab is refreshed and focused instead of duplicated. | Service-worker lifecycle regression for singleton, batch, duplicate finalization and existing-tab reuse. |
| DASH-02 | Dashboard data is PID-free by construction. | The dashboard receives only a whitelist projection containing numeric metrics, enumerated categories, opaque run/build/form references and timestamps. It receives no field values, labels, names, emails, uploaded filenames/content, screenshots, raw events, stack traces, confirmation IDs, full URLs, browser identity or arbitrary failure text. The page uses no network resources. | Projection-schema unit tests with PID canaries, source/manifest scan and rendered-text inspection. |
| DASH-03 | The default dashboard fits a widescreen viewport and explains results plainly. | At 1440×900 the header, four summary cards, primary visualization, chart controls and findings panel fit without document scrolling. Simple is the default view and every chart includes a short plain-language interpretation. | Static layout regression and managed-Chrome screenshot at 1440×900. |
| DASH-04 | Dashboard chart choices range from simple to advanced without inventing unsupported analysis. | The menu exposes Simple, Analyst, Statistical and Experimental groups. Simple charts work for one run; statistical and candlestick charts declare minimum comparable-history requirements and are disabled with an explicit reason when those requirements are unmet. | Chart-registry/data-availability regression and dashboard interaction test. |
| DASH-05 | Aggregate dashboard history is bounded and user controlled. | History retention is separately configurable, stores only the DASH-02 projection, retains at most 200 records and 90 days, and can be cleared from Settings or the dashboard. | Storage/history regression for disabled retention, bounds, expiry and clearing. |
| QUIET-01 | Routine console output remains quiet. | Normal operation produces no unnecessary browser-console noise. | Browser console inspection during a successful run. |
| DELV-01 | The extension is complete and usable. | All required extension files and installation and usage instructions are present in `output/`. | Inspect `output/` against `PROJECT.md`. |
